## 0. 上位原則(本ハーネスの正式な目的)

Goal Loopの目的は次の2つであり、品質最大化・速度最大化は目的ではない。

- **A. 要件適合性(Goal Alignment)** — 最初に定義したゴール・要件・制約に対して、最終成果物が正確に適合している確度を高める。「コードが動く」ではなく「作りたかったものを正しく作れているか」。
- **B. 未知の低減(Uncertainty Reduction)** — 開始時に認識できなかった要求・設計・UX・実装上の未知(特に無自覚の未知)を、仮説→実装→評価のループで発見・既知化する。

AIは未知に対して可能な限り自律的に仮説を立て、人間が評価可能な具体物まで精度を高めてから提示する。人間の役割は生成より評価。**ループ・テスト・レビュー・承認は、それ自体を目的とせず、AまたはBに寄与する場合にのみ実施する**(工程の存在理由テスト)。

「正しく作る」だけでなく、「最初には分からなかった正解を、作りながら発見する」ことがハーネスの価値である。

## 1. v0.1からの問題認識

- Superpowersの丁寧な工程 × Goal Loopのゲートが乗算で効き、MVPレベルの個人開発には重すぎた。
- マイルストーンが技術タスク単位に細分化され、1ループの実装価値が小さかった。
- 検証・管理に実装以上の時間を使うケースがあり、「ループを回すこと」自体の目的化リスクがあった。
- ユーザーが答えを持たない問いを人間へ返し続ける構造だった(無自覚の未知への対処が未設計)。
- グラレコ生成指示が曖昧で、CodexがAPIキー/スクリプト経由の生成を試みた。

## 2. 設計決定(D10〜D20。v0.1のD1〜D9に追加)

| ID | 論点 | 決定 | 根拠 |
|---|---|---|---|
| D10 | 目的再定義 | Goal Loopの目的をA(要件適合性)+B(未知低減)とする。終了条件は回数ではなく「適合性への十分な確信 + 残存する重要な未知が許容可能」 | メモ§3・§9 |
| D11 | ループ強度 | **MVP(既定)/高信頼の2段階**。Goal Frame作成時にFableが提案し、人間がGoal Frame確認時に確定。マイルストーン単位での一時変更も人間が指示可能 | メモ§2・§10-11。ユーザー決定(2026-08-10) |
| D12 | 仮定台帳 | goal直下に `assumptions.md` を新設。全フェーズで追記可。各仮定 = 内容 / 確信度(高・中・低) / 根拠 / **ゴールへの寄与1行** / 検証方法 / 状態(未検証・検証済み・棄却) | メモ§4〜§6。寄与1行は局所最適化ガード(ユーザー決定) |
| D13 | 仮説自律の境界 | **否定リスト方式**(§4参照)。リスト外は仮説を立てて自律的に進んでよい。リスト内はエスカレーションまたは人間確認 | ユーザー決定(2026-08-10)。肯定リストはエージェントの局所最適化を誘発するため不採用 |
| D14 | マイルストーン粒度 | 「**ユーザーが1つの価値をEnd-to-Endで利用できる**」単位を主基準とする。v0.1の5〜15分ルールは廃止し、「人間の受け入れテスト1回で確認できる」のみ残す | メモ§8 |
| D15 | 強度別工程表 | §3の表の通り。FableゲートとHuman Acceptanceは両強度で維持(Aの保証線) | メモ§8・§10-10/11 |
| D16 | 終了判定 | Approval Submissionに「残存未知リスト(重要度+許容可否の自己評価)」を必須化。Fableゲートは適合性+残存未知の許容性で判定し、重要未知が残る場合は対象未知を指定してREVISE | メモ§9。判定主体はFable(ユーザー決定) |
| D17 | レポート確信度区分 | Human Review Reportに「判断の内訳」を追加: 確定(検証済み) / 要件由来 / 仮説による決定(台帳参照) / 低確信・要確認 | メモ§6・§10-12/13 |
| D18 | 計測 | Retrospectiveの観測欄を拡張: ループ回数・呼び出し数・主要フェーズ所要時間(call-log.mdの時刻から算出)。トークンは計測不能のため回数×時間で代替 | メモ§10-15 |
| D19 | 未知の振り分け | ブレスト中、ユーザーが「決めていない/わからない」と答えた問いはその場で追及せず、**仮説化して台帳に記録し続行**する。Human Feedback(B-8/B-9)で発見された新規未知も台帳へ追記し、次ループ・次マイルストーンの入力にする | メモ§5・§10-14。Superpowers非改造のまま実行者(Opusメイン)の振る舞いとして規定 |
| D20 | グラレコ生成手段 | Codexの**組み込み image_gen ツールを直接使用**。APIキー設定・外部API呼び出し・生成スクリプト作成は禁止事項として明記(v0.1 D5の改訂) | 実地テストでの失敗(2026-08-10) |

## 3. 強度別工程表(D15)

| 工程 | MVP(既定) | 高信頼 |
|---|---|---|
| A-1 Goal Frame / A-6 Goal Gate | 実施(未知マップ+強度+終了条件を含む) | 同左 |
| B-1 マイルストーン開始確認(Fable) | 実施(軽量) | 同左 |
| B-2 実装委譲 | **E2E価値単位でまとめて `codex exec` に委譲可**(タスク細分化しない)。仮定台帳の関連仮定をプロンプトに含める | タスク分解して個別に委譲 |
| B-3 タスク単位の受け入れ | codexの自己検証報告の確認のみ(diff精読なし) | Opusメインがdiffを確認 |
| テスト要求 | **受け入れ基準に直結する検証 + 未知低減に効く検証のみ**を指定 | 単体・結合・lint・型検査をフル要求 |
| B-5 独立レビュー | **省略**。Opusメインがsubmission作成時にセルフチェック(goal-frame承認基準との対応 + 残存未知の列挙) | Opusサブエージェントで実施(PL-003) |
| B-6 Implementation Gate(Fable) | 実施(適合性 + 残存未知の許容性) | 同左 |
| B-7 Human Report / B-8 Acceptance | 実施(判断の内訳つき) | 同左 |
| Learning(Retro + グラレコ) | 実施(グラレコ失敗は非ブロック) | 同左 |

## 4. 仮説自律の否定リスト(D13)

以下に触れる仮説は自律実行禁止。エスカレーション(Fable)または人間確認を必須とする:

1. データ削除・上書き等の**不可逆操作**
2. **外部公開・送信**(デプロイ、外部APIへの送信、メール等)
3. **課金・支払い・契約**
4. **セキュリティ・認証・個人情報**の扱いの変更
5. Goal Frameに明記された**制約・要件の変更**(=要件の再定義)
6. 承認済み設計の**破壊的変更**

上記以外は、仮説を立て仮定台帳に記録した上で自律的に進んでよい。各仮定に「ゴールへの寄与」1行を必須とし(局所最適化ガード)、Fableゲートは台帳を入力に含めて仮定が事実扱いされていないかを確認する。

## 6. Fableゲート契約の改訂(v0.1 §9の差分)

- 入力: goal-frame.md + 対象文書 + **assumptions.mdの関連部分**(未検証仮定)
- 判定観点: v0.1の「承認基準を満たすか」に加えて、(1) 残存する重要な未知が許容可能か (2) 仮定が事実として扱われていないか (3) 否定リスト違反の仮説がないか
- REVISE時は戻り先工程に加えて**対象の未知・仮定を指定**する

## 7. 受け入れ基準(v0.2固有)

1. Goal Frame作成時にループ強度が提案され、人間が確定できる
2. MVP強度で1マイルストーンを回したとき、独立レビュー(Opusサブ)とタスク単位のdiff精読が発生しない
3. ブレスト中の未回答質問が仮定台帳に記録され、ループが停止しない
4. Approval Submissionに残存未知リストがあり、Fableゲートが未知の許容性を判定根拠に含める
5. Human Review Reportで「仮説による決定」と「確定事項」が区別されている
6. Human Feedbackで発見された未知が台帳に追記され、次ループの入力になる
7. 否定リスト該当の仮説が自律実行されない(エスカレーションされる)
8. グラレコがimage_genツールで生成される(スクリプト・APIキー使用なし)
9. Retroにループ回数・所要時間・発見された未知が記録される
