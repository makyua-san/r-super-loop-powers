# Fable 直接ヒアリング設計(RB-99)

作成日: 2026-11-06
対象: r-super-loop-powers Claude 版(`skills/r-super-loop-powers/`)
タスク: RB-99「fableを活かせてない気がする」
想定版: v0.11.0

以下で「利用者」は、このハーネスを使う人間を指す。各判断の出所を「利用者の決定」「作成者の判断」で区別する。作成者の判断は実装前に覆してよい。

## 1. 意図と背景

ゴール開始時の Fable に、別コンテキストからフラットに問う上流の役を果たさせたい。「本当にその機能が必要か」「優先度は」「あなたにとってどれくらい重要か」「他より優先するか」を問う役であり、具体的な機能の詰めは次の段の Codex が担当する。

### 今うまくいっていないこと

- 指示文が項目と手順を固定している(`references/workflow-a.md:40`)。「過去の不満・絶対に避けたい体験…」と列挙し、「感情・体験 → 嗜好・制約 → 検証」の順と「3〜7問」を指定している。
- 質問をまとめて出し、Opus が中継するので、利用者が整理された内容を直しながら詰める会話にならない(`references/workflow-a.md:41`)。
- Fable の入力が goal-seed、retro 抜粋、テンプレートに限られ(`SKILL.md:139`)、既存機能や他の作業を踏まえて問えない。
- 懸念がそのまま承認基準になり、重いテストに育つ。例: 電池の減りが気になる → 2 時間の電池消費を確認 → テストのたびに 2 時間かかる(`references/workflow-a.md:46`)。

### 実運用の記録から分かったこと

重複を除く 31 ゴールのうち 15 ゴール、初回ヒアリング 183 問を 1 エージェントが分類した。比率は目安である。

| 種類 | 問数 | 空振り率 |
|---|---:|---:|
| 認識ズレの修正 | 29 | 14% |
| 方針の調整 | 34 | 21% |
| ゴール・スコープ | 43 | 14% |
| メタ調整 | 14 | 14% |
| 定型 | 29 | 28% |
| 技術・HOW 寄り | 1 | 0% |
| 現状・利用場面の把握 | 33 | 6% |

- 定型は空振りしやすいが、機能した例もある。痛みのないゴールに不満を聞いたときに空振りが偏る。
- 他プロジェクトとの兼ね合いを問う質問はほぼない。
- 手持ちの資源が後から判明する抜けが複数ある。
- 複合質問は後半が落ちやすい。
- 問いでは防げない失敗がある。実物を見て初めて分かる好み、古い前提、spec への転記漏れである。
- 後段(A-2 以降)の技術寄りの問いは集計していない。

## 2. ゴール・非ゴール・避けたいこと

### ゴール

1. ヒアリングでは Fable が利用者と直接会話し、整理して返しながら問いを 1 つずつ詰める。
2. 問いは項目を埋めるためではなく、ゴールに合わせて目的から考える。
3. 答える負担を減らす。推奨付きの選択肢は選択画面で選べるようにする。
4. MVP モードでは、受け入れの既定を稼働テストにする。懸念と受け入れ条件を分ける。

### 非ゴール

- プロジェクトごとの設計書(機能の説明と到達度。Codex が作成・更新)。別タスクとする(6 章)。
- Codex 版(`skills-codex/`)への反映。作成者の判断。
- ゲート Fable の役割、A-5 以降の工程の変更。ただし 4.6 の受け入れ条件の扱いに関わる箇所(A-6、技術 PM のアセス、B-2 の検証、B-6、評価パッケージ)を除く。
- 後段(A-2〜A-4)の代理ブレストの問いの改善。今回は引き継ぎだけを変える。

### 避けたいこと

- 定型の項目を別の定型(5 目的の順に 1 問ずつなど)に置き換える。
- 毎回の確認が増えて、利用者の負担が今より重くなる。
- Fable が具体的な機能や実装方式を詰める。
- 懸念を聞かなくなる。分けて残すのであって、捨てない。

## 3. 全体の流れ

```text
A-0  Opus: Goal Seed 保存、照合の依頼、材料の準備
     ↓ 利用者に /model fable を案内
A-1a Fable(メインセッション): 利用者と直接ヒアリング、記録
A-1b Fable(メインセッション): Goal Frame 作成、利用者が確定
     ↓ 利用者に /model opus を案内
A-2〜A-4 Opus: 新しい代理 Fable と技術 PM で代理ブレスト
A-5 以降: 変更なし(ゲートは別インスタンスのゲート Fable)
```

利用者の決定: Fable が直接会話する。ヒアリングの中継はなくす。

## 4. 設計

### 4.1 モデルの切り替え

Claude Code の公式文書で確認した事実:

- メインセッションのモデルを変える手段として文書で確認できたのは、人間の `/model` だけである。
- スキルの `model` 指定はそのターンの残りだけ有効で、次の発話で戻る。複数ターンのヒアリングには使えない。
- 切り替え直後のターンはキャッシュが効かず、全履歴を読み直す。
- サブエージェントは `AskUserQuestion` を使えない。
- 切り替え後も文脈が保たれることを明記した一文は確認できていない。5 章で実機確認する。

切り替えの設計:

- A-0 の完了後に Opus が `/model fable` を案内して止まる。
- A-1b の確定後に Fable が `/model opus` を案内して止まる(戻す位置は作成者の判断)。
- 起動時チェックのモデル確認(`SKILL.md:17`)は、state.md の phase が `goal-definition` で A-1a / A-1b の間だけ Fable を正とする。それ以外は今のまま Opus を正とする。A-1a / A-1b の判別方法は builder に任せる。
- Fable を使えないとき(利用上限など)は、利用者の明示的な指示があれば Opus が同じ指示でヒアリングする。記録にその旨を残す(作成者の判断)。

### 4.2 ヒアリング前の材料(A-0)

Fable に渡す材料を、Fable の開始前に Opus が揃える。Fable の消費を増やさないためである(作成者の判断)。

1. **Codex の照合:** `bin/scout.ps1`(既存の読み取り専用スカウト)に、Goal Seed と関係する既存機能、被り、「拡張か新規か」の候補を問う。根拠のない結論は事実として扱わない。失敗してもループを止めない(スカウトの既存の規則)。
2. **既存の材料:** goal-seed、直近の retro 抜粋(今と同じ)、仮定台帳。
3. **他の作業の一覧:** Linear の接続があれば、利用者の進行中の課題を読み取りで一覧にする。接続がない、または取得に失敗した場合は、その旨を Fable に伝えて続ける(作成者の判断)。

設計書の仕組みが入るまで、照合は実装だけを相手にする。

Fable は上流の問いのために材料を読む。「既存の X の拡張で足りるか」は問うが、技術的な良し悪しは判定しない。

ヒアリングの途中で新しい事実が必要になったら、Fable は自分で `bin/scout.ps1` に問いを投げてよい。対象コードを Fable が直接読むことはしない(PL-009 のまま)。待つ間も会話は続け、スカウトの失敗はヒアリングを止めない。`references/roles.md` のスカウト節の「Opus から渡された問い」に、ヒアリング中の Fable を加える(作成者の判断)。

### 4.3 Fable への指示(A-1a の置き換え)

`references/workflow-a.md:37-41` の指示を、次の内容に置き換える。文言は builder が整えてよいが、次の要素を落とさない。

**役割**
- 別の視点から上流を問う。指示された要求をそのまま受け取らない。
- 目的は要件の項目埋めではなく、このゴールで利用者が本当に欲しいものと、やるべき範囲を一緒に確かめること。

**問いの目的**(順番も問数も固定しない。ゴールに関係するものだけ選ぶ)
1. 要求の認識ズレの修正
2. 方針の調整(Web の事例を参考にしてよい)
3. ゴールとスコープの設定
4. メタ調整(全体のリソース、利用者の状況、他プロジェクトとの兼ね合い、手持ちの資源)
5. 現状と利用場面の把握

**必ず聞くこと**
- MVP か高信頼かの確認のみ。利用者の決定: ワークフローの分岐なので残す。

**会話の型**
1. 利用者の話を受ける。
2. 整理して返す。見つけた事実や案も添える。推測は推測と明記する。
3. 利用者が直す。
4. 次に決めたいことを 1 つだけ問う。複合質問にしない。
5. 固まったら Goal Frame に進む。

**答えやすさ**
- 選択肢が立つ問いは、`AskUserQuestion` で推奨付きの選択画面を出す。
- 利用者に描写してほしい問いは、自由回答にする。選択肢で答えを誘導しない。

**止めること**
- 項目リストに沿った質問。痛みのないゴールに不満を聞くこと。
- 具体的な機能や実装方式を詰めること。Codex に任せる。ただし「利用者が名指しした手段は固定か候補か」は制約の確認として問ってよい。
- 回答できない問いの追及。今と同じく仮説化して assumptions.md に記録する。

**終わりの判断**

回数ではなく内容で判断する。次を利用者に返して合意できたら終わる。項目を順に質問するのではなく、まとめとして示し、未確認のものだけを問う。

- 何のためにやるのか
- なぜ今で、他より優先するのか。必要性に疑問があれば率直に述べる
- 既存機能との関係(拡張か新規か)
- やること、やらないこと
- 受け入れ条件と、運用で見る懸念(4.6)

目安だった「2〜4 往復」はなくす。

### 4.4 Haiku に任せる作業

利用者の決定: Web の事例、HTML のモック、推奨付きの選択画面を作る作業は Haiku でよい。

Fable は Agent ツールで `model: "haiku"` のサブエージェントに依頼する。

| 作業 | Haiku が返すもの | Fable がすること |
|---|---|---|
| Web の事例 | 事例の要点と出典 URL | 採否を判断し、整理して利用者に示す |
| HTML のモック | ローカルの HTML ファイルのパス | 利用者に見せて認識を合わせる |
| 選択画面 | 選択肢、推奨、理由の案 | 確認して `AskUserQuestion` で表示する |

- 選択画面の表示はメインセッションの Fable が行う。サブエージェントは `AskUserQuestion` を使えないためである。
- 簡単な選択肢は、Haiku に頼まず Fable が直接作ってよい(作成者の判断)。
- モックは認識合わせの道具であり、承認しても実装方式の決定にはならない。
- HTML はゴールディレクトリの `hearing/` に保存する。Artifact として公開しない(作成者の判断)。外部へ出す判断は既存の否定リストに従う。
- 検索語に秘密情報、個人情報、未公開の詳細を含めない。
- 呼び出しごとに `loop-log.ps1` に記録する。`-Who` に `haiku` を追加する必要があるかは builder が確認する。

### 4.5 記録と引き継ぎ

- `hearing-log.md` は Fable が会話のたびに追記する。利用者の回答は原文で残す。ヒアリングの会話を読んでいない後段の担当が、これを根拠にするためである。
- テンプレートの項目を今の会話の型に合わせて直す。例: 「過去の不満」に偏った説明の修正、「整理して返した内容」「利用者の修正」の追加。
- Goal Frame の確定後に `/model opus` へ戻し、以降の工程は今と同じファイルを正本として進む。
- A-2 の開始時に、Opus が新しい名前付きの代理 Fable を起動する。入力は goal-frame、hearing-log、ロール憲章である。ヒアリングをしたのは別の文脈(メインセッション)なので、記録だけで答えられることが条件になる。
- 代理 Fable が生きている区間は `A-1a〜A-4` から `A-2〜A-4` に変わる。`SKILL.md:154,184,185` と `references/workflow-a.md:3` の境界リセットの記述を合わせる。
- 代理ブレストの根拠を記録に限るため、記録にない固有の判断は今と同じく `ASK_HUMAN:` で利用者に戻す。
- 高信頼を選んだ場合: 深掘りを打ち切る点は今と同じ。直接会話するのは開発タイプの確認までとし、Goal Frame は新しい Fable インスタンスが作る今の流れのままにするか、メインの Fable が作るかは、記録の残し方に影響しないので builder が決めてよい。切り替えの回数が少ない方を選ぶ。

### 4.6 受け入れ条件の扱い(MVP のみ)

利用者の決定: MVP モードでは稼働テストだけでよい。時間のかかるテストは運用しながらでよい。高信頼モードには適用しない。

**分け方**

| 分類 | 扱い | 例 |
|---|---|---|
| 受け入れ条件 | 確認するまで受け入れない | アプリが起動して主要な操作が動く。出力形式が正しい |
| 運用で見る懸念 | 記録だけして、使いながら確かめる | 電池の減りが気になる |

**受け入れ条件の中身**

利用者の決定: 稼働テストに加えて、短時間で確かめられる要件ごとの確認は残す。削るのは時間のかかる実測だけである。

- 稼働テスト: 実際に起動し、ゴールの主要な操作が一通り動くこと。
- 要件ごとの短い確認: 出力形式、決めた制約など。「動くが作りたかったものと違う」を防ぐためで、要件適合性(`policy.md:10`)の保証線は変えない。
- 確認する担当は今と同じ。実装役の検証(B-2、`impl-check.ps1`)と、Checkpoint での利用者の受け入れ(作成者の判断)。

**時間の基準**

- 1 回の確認に 10 分を超える実測は、既定で「運用で見る懸念」に送る。10 分は作成者の仮の値で、利用者が変えられる。実測の結果に応じて見直す。
- 10 分以内の確認は、Fable が自分の判断で受け入れ条件にしてよい。利用者への確認は要らない(作成者の判断。確認を増やさないため)。
- 既存の否定リスト(課金、不可逆な操作、セキュリティなど)に触れる確認は、この既定で省略しない(作成者の判断)。

**10 分を超える実測を受け入れ条件に上げるとき**

Fable が選択画面で確認する。問いは「これが確認できないと受け入れられませんか?使いながら見るので足りますか?」、推奨は「使いながら」とする。利用者が選んだ場合だけ受け入れ条件にする。

**後の工程にも同じ既定を適用する**(作成者の判断。Goal Frame だけ直すと plan 側で同じ問題が再発するため)

- 代理ブレスト(A-2〜A-4)で新しい懸念が出たら、代理 Fable が同じ基準で分類する。10 分を超える実測を受け入れ条件にしたい場合は、`ASK_HUMAN:` で利用者に確認する。
- 技術 PM の実装アセスの「完了を示す検証コマンド」と、B-2 の検証にも、10 分の既定を適用する。超えるものは運用で見る懸念として記録する。
- B-6 では、運用で見る懸念は許容済みの未知として扱い、差し戻しの理由にしない。

**変更箇所**

- `templates/goal-frame.md` に「運用で見る懸念」の節を足す。
- A-1b の指示に、この分け方を足す(`references/workflow-a.md:46`)。
- A-2〜A-4 の代理 Fable への依頼文と、技術 PM 共通契約の実装アセス(`references/workflow-a.md:27,58`)。
- A-6 のゲート判定に「10 分を超える実測が、利用者の確認なしに承認基準に入っていないか」を足す(MVP のみ)。
- `references/workflow-b.md` の B-2 の検証と B-6 の判定観点。
- Checkpoint の評価パッケージで、運用で見る懸念を一覧にして渡す。
- `policy.md` のテスト要求の行(MVP)と矛盾しないように合わせる。

### 4.8 やらないと決まったときの終わり方

利用者の決定: 理由を記録して閉じる。新しい状態は増やさない。

- ヒアリングで Fable と利用者が「やらない」「後回し」「既存の別ゴールに合流」と合意したら、Goal Frame を作らずにそのゴールを終える。
- `hearing-log.md` に結論と理由を書く。後回しなら再開の条件、合流なら合流先と引き継ぐ内容も書く。
- state.md は既存の終了状態(`phase: done`)にする。結論の種類は記録に書く。Stop フックと再開の判定は既存の `done` の扱いのまま動く。
- Fable が `/model opus` へ戻すよう案内する。retro は作らない(作成者の判断)。
- rb のタスクから始まったゴールなら、結論を rb に報告する。

## 5. 確認方法

自動テストは既存の `tests/*.tests.ps1` を通す。ヒアリングの質は自動では測れないので、実ゴール 1 件のスモークで確認する。

1. `/model` の切り替え後に文脈が保たれるか(未確認の事実の確認)。
2. Fable がメインセッションで `AskUserQuestion` を使えるか。
3. A-2 の代理 Fable が記録だけで答えられるか。
