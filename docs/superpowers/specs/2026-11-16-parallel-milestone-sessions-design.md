# マイルストーンの並行セッション(RB-116)

以下で「利用者」は、このハーネスを使う人間を指す。各判断の出所を「利用者の決定」「作成者の判断」で区別する。作成者の判断は実装前に覆してよい。

## 1. 意図

1 つのゴールの中で、互いに干渉しないマイルストーンを**別々のメインセッション**で同時に進める。

狙いの順位(作成者の判断、利用者と議論済み):

1. **精度** — 1 セッションの文脈が 1 マイルストーンだけになり、他の話題に引っ張られない。
2. **人間の認知負荷に合わせる** — 1 セッション = 1 マイルストーンで「今何をしているか」が 1 行で言える。並行数の上限は人間が追える数で決める。
3. **サイクル短縮** — 片方の判断待ち・差し戻しで、もう片方が止まらない。
4. コストは分割の理由にしない(各セッションが共通文脈を読み直す分、むしろ増える)。

### 採らなかった案

- **進行役は 1 つ、実装役(Sonnet)だけ並行** — 利用者の判断「これまでと変わらない」。速くなるのは B-2 の待ちだけで、B-4 の人間待ちや B-5〜B-6 は直列のまま。
- **別々のゴール同士の並行** — 将来必要(利用者の決定)。rb-2tl に起票済み。

## 3. 構成

### 3.1 前提: 正本はリポジトリの中にある

ゴールの記録(`docs/r-super-loop-powers/<goal-slug>/`)は対象リポジトリの作業ツリーの中にある。作業ツリーを分けると、**記録も子ごとの写しになる**。そこで「共有ファイルを全員で書く」のではなく「子は自分の作業ツリーの写しだけを書き、合流で統合する」とする。

### 3.2 置き場所と持ち主

| ファイル | 書く者 | 合流での扱い |
|---|---|---|
| `<goal>/state.md`(親) | 分割時(A-4 後)と合流時だけ | 合流担当が並行区間を閉じる |
| `<goal>/parallel.md`(新) | 分割時に作る。各子は自分の行だけ更新 | 並行の台帳: マイルストーン・ブランチ・作業ツリーの絶対パス・状態(running / passed / halted) |
| `<goal>/milestones/<n>-*/state.md`(子、新) | その子だけ | 合流後は読むだけ |
| `milestones/<n>-*/` の他(submission・gate-decision・decisions) | その子だけ | ディレクトリが別なので衝突しない |
| `impl-runs/`・`codex-runs/` | 子(ラベルにマイルストーン番号を含める) | ファイル名が別なので衝突しない |
| `assumptions.md`・`call-log.md`・`hook-log.md` | 子が追記だけ | `.gitattributes` の `merge=union` で行を合併 |
| `design.md`(設計書) | 子は書かない | Learning(合流後)で従来どおり更新 |

### 3.3 流れ

1. **分割(A-4 の後)**: goal-plan.md の同じ Checkpoint 内のマイルストーンについて、Fable(要件)と Codex 技術 PM(ファイル・インターフェース)にそれぞれ「並べてよい組」を出させる。両方に出た組だけが候補。利用者に提示し、了承されたら次へ。
2. **準備**: マイルストーンごとにブランチと作業ツリーを作り、`parallel.md` と子の `state.md` を置いてコミットする。各作業ツリーに再開の印(`resume-pending`、`cwd:` はその作業ツリー)を置き、利用者に「この 2 つのフォルダでそれぞれセッションを開いて『続けて』」と頼む。セッションを自動で開く手段は無い。
3. **並行**: 子は再開パケットから自分の `state.md` を読み、B-1〜B-6 を回す。B-1 で疎結合を軽く再確認する。中間クローズ(非 Checkpoint の PASS 後の中間コミット)は自分のブランチに対して行う。
4. **合流**: B-6 PASS した子は `parallel.md` の自分の行を `passed` にし、兄弟の作業ツリーの `parallel.md`(絶対パスで読む)を見る。
   - 兄弟がまだ `running` → 「相手の完了待ち」で印を置いて止まる。
   - 兄弟が `passed` → 自分が最後なので合流担当になる。ベースのブランチへ順にマージし、全体の検証(テスト等)を流し、親 `state.md` を戻して B-7(Checkpoint の評価パッケージ)へ進む。
5. **外れたとき(D5)**: 子の B-4・B-9 で、もう片方のマイルストーン定義に触れる戻りになったら、`parallel.md` を `halted` にし、もう片方にも止まるよう利用者に伝える。以後は直列。

### 改訂(作成者の判断)

- **R-a 並行の台帳はリポジトリの外に置く。** `parallel.md` を追跡ファイルにせず、全作業ツリーが共有する git の共通ディレクトリ(`git rev-parse --git-common-dir` の下、例 `rslp-parallel/<goal-slug>/`)に置く。担当の選出はそこでの排他作成(`<goal-slug>/merger` を作成済みなら失敗する)で行う。最初に作れた子が「相手が passed か」を見る。passed なら担当になり、まだなら作ったものを消して待つ。台帳はゴール終了時に合流担当がゴール記録へ写しを残す。これで R1 と R5 を同時に解く。
- **R-b 子の状態は、子の作業ツリーにある普通の `<goal>/state.md` にする。** 作業ツリーごとに写しがあるので、それぞれが自分のマイルストーンの状態を持てばよい。`milestones/<n>/state.md` は作らない。フック・`loop-log.ps1`・`resume-packet.ps1` は変更しなくて済む(3.2 の表の「親」「子」の行はこれで置き換える)。親の状態はベースの作業ツリーの `state.md` で、分割中は `phase` が「並行中」であることを示す。合流で `state.md` が衝突したら、合流担当が親の状態を書き直す。
- **R-c PASS を公開する前に確定コミットする。** 子は B-6 PASS の後、実装と判定記録を自分のブランチにコミットし、その SHA を台帳に書いてから `passed` にする。合流はその SHA に固定する。
- **R-d 合流はベースの作業ツリーで行う。** 合流担当(子のセッション)は `git -C <ベースの作業ツリー>` で操作する。開始条件は、ベースの作業ツリーがきれい(未コミット変更なし)であること。
- **R-e ログの行にマイルストーン番号を足す。** `hook-common.ps1` の追記行に、作業ツリーの state.md の milestone を入れる。retro の件数集計が並行区間で減らないようにするため。
- 3.3 の「準備」で `parallel.md` をコミットしていた部分は R-a で台帳作成に置き換える。
